## Entry ownership and late native work

A UI deadline does not cancel Tauri or OS work. The shared entry controller keeps a pending operation until its promise settles. An abandoned attempt requests cleanup immediately, even if enable never resolves or rejects after partial application. A successful navigation commits ownership to the contest lifecycle; late completion must not recreate an onboarding cleanup callback.

Integration found and corrected both `commit → late completion → unmount` and `commit → unmount → late completion` cases. The controller tests also cover failed attempts with already-acquired or pending native state, rejected enable, overlap retention, and cached waiver refresh on failure/timeout. Windows/macOS/unknown platforms use immediate plus post-settlement cleanup because their preparation can precede native serialization; the pending key remains owned through cleanup so an old attempt cannot remove a new retry's rules. Only confirmed Linux relies solely on its native epoch guard. The real final-entry callback is exercised by the existing source-derived integration fixture.

Linux now runs blocking DNS/helper work off the async worker. A preparation ticket and deadline are checked under the mutation lock before applying rules. Cleanup invalidates old tickets before waiting for an admitted operation to finish, then restores in order. Pending or failed cleanup blocks new network admission until a successful retry. A rejected or panicked admitted helper transaction also latches recovery before another enable can start. Shutdown closes admission permanently. A DNS-only result cannot produce a firewall when no requested API destination resolved.

These bounds do not claim OS DNS or an already-admitted helper transaction is forcibly cancellable. Cleanup is ordered after admitted work; the durable token remains the recovery capability when completion is uncertain.

## Startup firewall recovery

Before creating the webview/login flow, the Linux app acquires and retains a private per-user kernel file lock, restores keyboard leftovers, and calls the existing token-authenticated network disable path. The helper's restart reconciliation alone was insufficient: its daemon may still be running after a GUI crash, and its old allowlist may not fit a new hotspot.

The lock prevents a second cooperating GUI instance from clearing the first one's protections. Missing state-directory ancestors are created for first launch; the final directory/file must be private, owned, regular and not a symlink. A stale lock file is reused rather than unlinked; the kernel releases ownership when its process dies. Tests cover exclusion, reacquisition, stable inode reuse, missing parents and unsafe lock rejection.

Recovery failures remain visible through native restore status and retain the token/journal for retry. No blind `iptables` flush, token invention, or other-user marker deletion was introduced. An older app version does not participate in the new instance lock: close old versions before upgrading/testing the new one. A missing/corrupt token or unavailable helper can still require administrator recovery.

## GNOME timing and KDE coverage limits

The review's weak-laptop timeout is a plausible runtime failure, not a measured affected-device reproduction. The current GNOME adapter performs about six subprocesses per newly supported key, plus schema/key discovery—roughly 500 calls for 83 keys, rather than the review's estimated 750. Discovery was already cached. This revision fixes failure-scope leakage; it does **not** claim batching or a measured speedup. Slow hosts can return partial coverage within the bound. A genuinely required organizer keyboard policy is still enforced.

KDE configuration/readback and accepted D-Bus calls require live Plasma 5/6 validation. “Active” refers to verified discovered control families, not every shortcut, gesture or compositor escape path. Cinnamon remains unsupported. No host desktop state was mutated for these tests.

## Follow-up recovery review fixes

The follow-up review reproduced two gaps in combined failure paths. Secure startup now uses required resource ownership: it still blocks on failure/timeout, but retains an unlock callback until successful entry commits. Abandonment requests immediate cleanup and cleanup after a pending startup settles. A retry checks that resource before collecting native device state, preventing a new Linux probe from colliding with the old desktop owner. Reusing the existing resource controller keeps the same cancellation/commit ordering as network ownership; merely adding an unlock in the catch handler would miss late native startup. Native restoration failures continue to require the existing explicit system-settings recovery.

Contest preview cleanup now explicitly preserves camera hotplug recovery. Ordinary video release still suppresses automatic reopening when leaving Settings. Removing that suppression globally would reopen cameras after an intentional release; retaining it for contest retries would strand monitoring after failed reopen attempts. Exact device selection and audio ownership are preserved.

New controlled regressions cover post-start verification rejection followed by successful retry, verification timeout with pending cleanup, late startup after timeout/cancellation, and exact-camera replug after preview cleanup and exhausted retries. These are source/fixture checks, not installed desktop or hardware acceptance; Phase G remains open.

Follow-up validation: all **689 web tests** passed (five new recovery scenarios), along with web typecheck and diff whitespace checks. Rust, package builds and physical desktop tests were not rerun for these TypeScript-only recovery changes.
