System Architecture

The platform is partitioned into four planes: Client Plane (Next.js, native exam shell), Application Plane (Go API, Supabase Auth, Realtime), Execution Plane (judge workers, sandboxes), and Storage Plane (Supabase Postgres, S3, Redis). Each plane scales independently.

Design principle: The Go API layer is the single source of business logic. Supabase handles auth and provides direct Postgres access with Row Level Security for the frontend where appropriate. Judge nodes are air-gapped from the public internet and talk only to SQS and S3.

Why Supabase over Raw RDS + Custom Auth

Supabase provides Postgres (with RLS), Auth (JWT, OAuth, MFA, magic links), Storage (S3-compatible), and Realtime (Postgres change streams over WebSockets) as a unified SDK. This eliminates 3–4 custom services that would otherwise take significant engineering time to build and secure. For a contest platform, Supabase Realtime's channel-based pub/sub directly replaces a custom WebSocket broadcast layer for verdicts and rankings.

Supabase in production: Run on Supabase Pro or deploy self-hosted (supabase/supabase Docker Compose on EC2) for data sovereignty, custom VPC placement, and no row-count limits. Self-hosted is recommended when your Postgres load exceeds ~500 concurrent connections or you need to colocate with judge nodes.
B

Auth & Multi-tenancy

Authentication is handled entirely by Supabase Auth. The platform wraps it with an organization-scoped RBAC layer enforced both in the Go API (middleware) and in Postgres (RLS policies). Every authenticated request carries a signed JWT containing user_id, org_id, and role.

Auth Flows

CORE

Email + Password

Standard Supabase email auth with email confirmation. Rate-limited via Supabase Auth settings. Use for contestant self-registration.

CORE

Magic Link / OTP

Passwordless invite-based onboarding. Ideal for org admins inviting team members and candidates to specific contests.

EXTENDED

OAuth (Google, GitHub)

One-click social login. Reduces registration friction for open contests. Supabase handles token exchange and user upsert automatically.

EXTENDED

SAML 2.0 / SSO

Enterprise requirement. Supabase Auth supports SAML via the Enterprise plan, or proxy through Auth0/Okta and issue Supabase sessions post-validation.

Row Level Security

RLS — contests table
ALTER TABLE contests ENABLE ROW LEVEL SECURITY;

-- Participants can only see contests they are registered for OR public ones
CREATE POLICY "contestant_read" ON contests
  FOR SELECT USING (
    visibility = 'public'
    OR org_id IN (
      SELECT org_id FROM org_members
      WHERE user_id = auth.uid()
    )
  );

-- Only org admins and above can insert/update contests
CREATE POLICY "admin_write" ON contests
  FOR ALL USING (
    org_id IN (
      SELECT org_id FROM org_members
      WHERE user_id = auth.uid()
        AND role IN ('owner', 'admin')
    )
  );
C

Database Design

Supabase Postgres is the primary datastore. The Go API owns all writes through prepared statements. Supabase's direct PostgREST endpoint is used by the frontend only for read-heavy, RLS-protected queries (e.g. live ranking fetches, problem statements). Critical paths (submission pipeline, verdict writes) always go through the Go API.

Core Schema

SQL — full contest schema
CREATE TABLE contests (
  id              uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id          uuid        REFERENCES organizations(id) ON DELETE CASCADE,
  title           text        NOT NULL,
  slug            text        UNIQUE NOT NULL,
  status          text        NOT NULL DEFAULT 'draft',  -- draft|review|scheduled|live|ended
  visibility      text        NOT NULL DEFAULT 'public', -- public|private|invite_only
  start_time      timestamptz NOT NULL,
  end_time        timestamptz NOT NULL,
  freeze_time     timestamptz,                              -- null = no freeze
  scoring_type    text        NOT NULL DEFAULT 'icpc',    -- icpc|ioi|custom
  config          jsonb       NOT NULL DEFAULT '{}',
  created_at      timestamptz DEFAULT now()
);

CREATE TABLE problems (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id          uuid REFERENCES organizations(id),
  title           text NOT NULL,
  statement_md    text NOT NULL,
  checker_type    text NOT NULL DEFAULT 'exact',           -- exact|custom|checker
  checker_code    text,
  time_limit_ms   int  NOT NULL DEFAULT 2000,
  memory_limit_mb int  NOT NULL DEFAULT 256,
  status          text NOT NULL DEFAULT 'draft',            -- draft|review|approved
  created_by      uuid REFERENCES auth.users(id)
);

CREATE TABLE contest_problems (
  contest_id      uuid REFERENCES contests(id)  ON DELETE CASCADE,
  problem_id      uuid REFERENCES problems(id),
  label           text NOT NULL,                             -- "A", "B", "C"...
  points          int  NOT NULL DEFAULT 100,
  PRIMARY KEY (contest_id, problem_id)
);

CREATE TABLE submissions (
  id              uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  contest_id      uuid        REFERENCES contests(id),
  problem_id      uuid        REFERENCES problems(id),
  user_id         uuid        REFERENCES auth.users(id),
  language        text        NOT NULL,
  code_s3_key     text        NOT NULL,                      -- code stored in S3, not DB
  status          text        NOT NULL DEFAULT 'pending',
  verdict         text,                                       -- AC|WA|TLE|MLE|RE|CE|SE
  score           int,
  time_ms         int,
  memory_kb       int,
  judge_output    text,
  submitted_at    timestamptz DEFAULT now(),
  judged_at       timestamptz
);

-- Partial index: only index pending/judging submissions for fast queue polling
CREATE INDEX idx_submissions_pending ON submissions(submitted_at)
  WHERE status IN ('pending', 'judging');
Source code in S3, not Postgres. Submission code is stored as submissions/{submission_id}/solution.{ext} in S3. The code_s3_key column holds only the object key. This keeps the Postgres row small (fast ranking queries) and avoids large text payloads in WAL replication.

Ranking Materialization

Rankings are not recomputed on every read. A lightweight Go process (the Ranking Updater) subscribes to the Supabase Realtime submissions channel, receives INSERT/UPDATE events on verdict changes, and updates a leaderboard table + a Redis sorted set in a single atomic operation. The frontend reads from Redis (via API) for live updates and falls back to Postgres for historical views.

SQL — leaderboard table
CREATE TABLE leaderboard (
  contest_id      uuid REFERENCES contests(id) ON DELETE CASCADE,
  user_id         uuid REFERENCES auth.users(id),
  total_score     int  NOT NULL DEFAULT 0,
  penalty_secs    int  NOT NULL DEFAULT 0,           -- ICPC-style
  solved_count    int  NOT NULL DEFAULT 0,
  last_accept_at  timestamptz,
  rank            int,                                -- precomputed, updated by Ranking Updater
  is_frozen       bool NOT NULL DEFAULT false,
  updated_at      timestamptz DEFAULT now(),
  PRIMARY KEY (contest_id, user_id)
);

Sandbox Isolation — nsjail

Every submission executes inside an nsjail sandbox on the judge EC2 instance. nsjail uses Linux namespaces, cgroups v2, and seccomp-bpf syscall filtering to isolate untrusted code. This is the first tier of isolation; the second tier is that judge instances sit in a dedicated private subnet with no inbound internet routing.

bash — nsjail execution command
nsjail \
  --mode o \
  --time_limit 4 \              # 2× the problem limit; wall-clock safety
  --rlimit_as 512 \             # address space (MB)
  --rlimit_cpu 3 \              # CPU seconds
  --rlimit_nproc 1 \            # no fork()
  --rlimit_nofile 32 \          # restrict file descriptors
  --disable_proc \               # hide /proc
  --iface_no_lo \                # no loopback = no network
  --user 65534 --group 65534 \ # nobody:nogroup
  --chroot /sandbox/rootfs \
  --cwd /sandbox/work \
  --seccomp_string "ALLOW { read, write, exit_group, brk, mmap, ... }" \
  -- /sandbox/work/run.sh
MechanismWhat it enforcesImplementation
cgroups v2CPU time, memory, PIDsmemory.max, cpu.max, pids.max=1
Linux namespacesIsolated filesystem, process tree, network, IPCmount/pid/net/ipc/uts ns
seccomp-bpfSyscall allowlist; any other syscall → SIGKILLAllowlist: ~40 safe syscalls for each language
rlimitsStack, open files, address space, nprocsetrlimit() before exec

Firecracker Upgrade Path

For Phase 2+ (hostile code, enterprise SLAs), migrate execution from bare nsjail on EC2 to nsjail inside Firecracker microVMs. Firecracker provides a separate guest kernel per submission, eliminating kernel-level side-channel attacks. Each VM boots in ~125ms; with snapshot pre-warming per language, this drops to <30ms. The judge worker API stays identical — only the sandbox driver changes.

go — judge worker interface (stable across nsjail / Firecracker)
type SandboxDriver interface {
  Execute(ctx context.Context, req ExecRequest) (ExecResult, error)
}

type ExecRequest struct {
  Binary       []byte
  Stdin        []byte
  TimeLimitMs  int
  MemLimitMb   int
}

type ExecResult struct {
  Stdout    []byte
  Stderr    []byte
  TimeMs    int64
  MemoryKb  int64
  ExitCode  int
  Verdict   string   // "AC" | "TLE" | "MLE" | "RE" | "RTE"
}

Autoscaling Strategy

Judge nodes run as an EC2 Auto Scaling Group on Spot instances (c6i.xlarge or c7i.xlarge). The ASG scales based on a custom CloudWatch metric: SQS ApproximateNumberOfMessagesVisible / target messages-per-node. Target: each node processes 1 submission per 3 seconds with one worker thread (serial per node to avoid noisy-neighbor inside sandbox).

PhaseLoadJudge nodesInstance typeSpot savings
Idle (non-contest)<5 subs/min1–2 (on-demand)t3.medium—
Pre-contest warmupRamp up4–8 (spot)c6i.xlarge~65%

Spot interruption handling: Judge workers must handle SIGTERM gracefully. On SIGTERM (2-minute Spot notice), the worker stops pulling new jobs, finishes the current submission (typically <30s), and returns the SQS message visibility. SQS will re-deliver it to another node within the visibility timeout. Never commit a verdict until the sandbox exits cleanly.
E

Realtime Layer

Supabase Realtime replaces a custom WebSocket broadcast server. It exposes Postgres change streams over WebSocket channels with row-level filtering. Contestants subscribe to their own submission channel and the contest leaderboard channel. The Go API's Ranking Updater writes verdict results directly to the submissions and leaderboard tables, and Supabase Realtime broadcasts the change to all subscribers automatically.

typescript — frontend Supabase Realtime subscription
import { createClient } from '@supabase/supabase-js'

const supabase = createClient(SUPABASE_URL, SUPABASE_ANON_KEY)

// Subscribe to own submission verdicts
supabase
  .channel(`submissions:${userId}`)
  .on('postgres_changes', {
    event: 'UPDATE',
    schema: 'public',
    table: 'submissions',
    filter: `user_id=eq.${userId}`
  }, (payload) => {
    updateSubmissionStatus(payload.new)
  })
  .subscribe()

// Subscribe to live leaderboard updates
supabase
  .channel(`leaderboard:${contestId}`)
  .on('postgres_changes', {
    event: '*',
    schema: 'public',
    table: 'leaderboard',
    filter: `contest_id=eq.${contestId}`
  }, (payload) => {
    updateLeaderboard(payload.new)
  })
  .subscribe()
Scale ceiling: Supabase Realtime supports ~500 concurrent connections per channel on the managed platform. For a 10k-contestant contest all subscribing to the same leaderboard channel, this requires either: (a) self-hosted Supabase Realtime scaled horizontally, or (b) a fan-out architecture where the Go API aggregates rank updates and pushes to a Redis Pub/Sub → custom WebSocket gateway. Implement (b) at the 5k+ contestant scale. Below that, Supabase managed handles it cleanly.

Problem Pipeline (Problemsetting Workflow)

  1. Create: Problem setter creates problem via CMS UI. Statement in Markdown, renders with KaTeX for math. Sample I/O attached.
  2. Upload testcases: Uploaded via signed S3 presigned URL. Go API validates format (input/output pairs). Stored at problems/{problem_id}/testcases/{n}.{in,out}.
  3. Checker: For problems requiring custom comparison (e.g. "any valid permutation"), attach a checker binary or select a built-in (exact, token, float-eps).
  4. Stress test: Problem setter submits a reference solution. The judge runs it against all testcases; if all pass, problem is marked ready for review.
  5. Review: Reviewer verifies problem statement clarity, testcase coverage, constraints. Approves or sends back with comments.
  6. Attach to contest: Approved problem is attached to a contest with a label (A, B, C...) and point value. Invisible to participants until contest goes live.

Application Security

CORE

JWT Auth via Supabase

Every API request carries a Supabase-signed JWT. Go API verifies signature locally (RS256, public key fetched from Supabase JWKs endpoint at startup).

CORE

Rate Limiting

Submission throttle: 1 submission per 5s per user per problem. Login attempts: 5/min per IP via Supabase Auth. Global API rate-limit via AWS WAF rules on ALB.

CORE

Input Validation

All API inputs validated with strict JSON schemas before DB writes. Code submissions size-limited to 100KB. Language allowlist enforced server-side (never trust client).

CORE

Audit Logging

All admin actions logged to audit_log table with actor, action, target, and IP. Immutable (no DELETE policy). Retained 90 days in S3 via CloudWatch Logs export.

EXTENDED

Secrets Management

All credentials (Supabase service role key, S3 keys, SQS URLs) in AWS Secrets Manager. ECS tasks and EC2 judge nodes use IAM roles; no static credentials in environment variables.

EXTENDED

Plagiarism Detection

Post-contest async job: compare all accepted submissions per problem using MOSS-style token fingerprinting. Flags suspicious pairs to org admin. Does not affect live verdicts.

Development Roadmap

Phase 1 — Working Contest Platform

Months 1–3 · 2–3 engineers · Target: run real contests
  • Auth + Orgs: Supabase Auth (email + GitHub OAuth), org creation, invite-based membership, RBAC middleware in Go.
  • Problem CMS: Markdown editor, testcase upload to S3, exact/token checkers, problem approval flow.
  • Judge v1: nsjail on a single EC2 instance, SQS-based job queue, Go judge worker, C++/Python/Java support.
  • Contest engine: Schedule contests, ICPC scoring, submission pipeline, manual ranking page (polling, not realtime yet).
  • Frontend: Next.js, Monaco Editor, contestant dashboard, basic admin UI.
  • Skip: Supabase Realtime (polling is fine for Phase 1), autoscaling, Firecracker, plagiarism detection, proctoring.

Phase 2 — Realtime, Scale, Multi-org

Months 4–7 · add 1–2 engineers · Target: 5k concurrent users
  • Supabase Realtime: Live verdicts and leaderboard via Postgres change events. Replace all polling.
  • Autoscaling judges: EC2 Spot ASG with CloudWatch SQS metric scaling. Pre-warming on contest start. Spot interruption handling.
  • Ranking Updater: Dedicated Go process, Redis sorted set for leaderboard, freeze/unfreeze logic.
  • IOI + CF scoring modes: Extend scoring engine with subtask partial credit and time-decay scoring.
  • Self-hosted Supabase (optional): Migrate if Postgres connection counts or Realtime limits become binding constraints.
  • Billing: Stripe integration, per-org subscription plans, contest capacity limits per plan.
  • Monitoring: Grafana dashboard (CloudWatch source), PagerDuty/Opsgenie alerts for judge queue depth and API error rate.

Phase 3 — Assessment Platform + Advanced Features

Months 8–18 · add platform engineer + ML eng · Target: 50k concurrent, enterprise
  • Firecracker microVMs: Replace nsjail with nsjail-in-Firecracker for kernel isolation. Pre-warmed VM snapshot pool per language.
  • Assessment modes: MCQ renderer, time-boxed open-ended questions, hybrid assessments. AI-assisted rubric scoring via Anthropic API (async, post-exam).
  • Proctoring (async): Webcam/screen capture to S3, event log, tab-switch detection. No live monitoring yet — async review UI for admins.
  • Plagiarism detection: Post-contest MOSS-style analysis job on accepted submissions. Similarity matrix report to org admin.
  • EKS migration: Move from ECS Fargate to EKS for cost efficiency at scale. Kafka MSK for event durability on anti-cheat pipeline.
  • SSO/SAML: Enterprise org SSO via Supabase SAML or Okta proxy. Required for university and enterprise customers.
  • Multi-region: US + EU deployment for GDPR compliance. Route53 latency routing. Separate Supabase projects per region.
  • SOC 2 Type II: Begin audit process. Required for enterprise SLAs. Implement audit log completeness, access reviews, and change management.

What This Architecture Deliberately Avoids

  • Kubernetes (Phase 1–2): ECS Fargate provides enough orchestration without the operational overhead of EKS. Migrate in Phase 3 when cost optimization at scale justifies it.
  • Kafka (Phase 1–2): SQS is sufficient for the submission pipeline. Add Kafka MSK only when event durability requirements for anti-cheat/proctoring pipelines demand it.
  • Custom WebSocket server: Supabase Realtime handles verdict and leaderboard broadcasting. The only custom WebSocket code needed is a fan-out gateway for >5k concurrent leaderboard subscribers.
  • Separate auth service: Supabase Auth eliminates the need for a custom auth microservice. The Go API enforces RBAC using the JWT claims issued by Supabase.
  • Microservices from day one: Start as a modular monolith. Extract the Judge Service in week 8, Media Ingestion in week 16. Everything else stays in the Go monolith until a concrete bottleneck forces a split.
