## Completion statement

Phase 2f replaces the earlier string-only migration confidence with an opt-in
real-PostgreSQL qualification suite. The complete embedded migration chain from
001 through 042 now applies on a fresh PostgreSQL 16.14 database, reruns as a
no-op, survives two simultaneous migration runners, enforces the candidate
projection and snapshot invariants exercised by the application, and rolls back
the known migration-041 and migration-042 preflight failures without leaving
partial schema or tracking rows.

The qualification and final independent diff audit exposed fresh-apply,
already-recorded upgrade, lifecycle, and concurrency defects that ordinary Go
tests did not detect. They are corrected and pinned by real-PostgreSQL runtime
tests.

This is representative PostgreSQL qualification, not production-version
qualification. The repository does not declare the deployed Cloud SQL major,
so the same suite must still pass against that exact major before rollout.

## Subagent-driven audit inputs

Three independent read-only audits reviewed schema invariants, migration-runner
behavior, and transaction races. They agreed on the following P0 findings:

1. migrations 038 and 042 used a nonexistent `num_nonnull` function instead of
   PostgreSQL's `num_nonnulls` built-in;
2. the migration runner had no cross-instance lock even though multiple API
   instances can start concurrently;
3. the DRAFT binding trigger read contest status without locking the contest
   row, so binding and publication could race; and
4. immutable projection identity did not close over the child asset count and
   total bytes at the point a question selected it.

The audits also identified session/question mutation fairness, exact snapshot
copying, late asset insertion, cxxprobe question-type drift, and status
regression as connected boundaries. Phase 2f closes those paths in migration
042 and exercises them on the disposable database.
The final audit additionally found that editing migration 039 could not repair
databases that had already recorded it, that cross-contest question moves could
bypass the source contest's frozen state, and that late-asset lookups needed
source-side indexes. Migration 042 now repairs and tests all three boundaries.

## Runtime defects corrected

### PostgreSQL function spelling

Every `num_nonnull(...)` call in migrations 038 and 042 is now
`num_nonnulls(...)`. Static tests require the plural built-in and explicitly
reject the singular spelling. Before this correction, a fresh real migration
failed atomically in migration 038.

### Archive-location uniqueness removal

Migration 038 relied on PostgreSQL's autogenerated name for the unique
`problem_bundles(storage_bucket, storage_object, storage_generation)`
constraint. Migration 039 attempted to drop a different truncation of that long
name, emitted a notice, and left the uniqueness active. This contradicted the
design allowing one content-addressed canonical archive to back more than one
question-scoped immutable bundle row.

Migration 038 now gives the constraint the stable name
`problem_bundles_archive_object_generation_unique`. Migration 039 drops both
names on fresh installs. A database that already recorded 039 will never re-run
that corrected file, so migration 042 repeats both compatibility drops. One
runtime test inspects the fresh catalog; another starts with migrations through
041 already recorded plus the legacy constraint restored, then proves 042
removes it and records the repair.

### Concurrent migration startup

`db.Migrate` now acquires one dedicated pool connection and a fixed PostgreSQL
session advisory lock before it creates/checks `schema_migrations`. Every
filename check and per-file transaction runs through that locked connection.
The lock is released with an independent bounded cleanup context; if unlock
fails, the underlying connection is closed so a pooled session cannot retain
the advisory lock.

Two simultaneous `Migrate` calls now both succeed while recording each embedded
migration exactly once. The test runs from an empty database, so it covers the
previous check-before-DDL race rather than only a no-op case.

### Binding and contest-status serialization

Both definitions of `guard_cxxprobe_question_binding_in_draft` now read the
owning contest `FOR SHARE`. A contest status update and a cxxprobe binding change
therefore share one row-level serialization point:

- if scheduling commits first, the waiting binding observes `SCHEDULED` and is
  rejected by `contest_questions_cxxprobe_draft_binding_check`; and
- if binding commits first, scheduling waits, then succeeds with the complete
  immutable identity already selected.

The integration suite runs both transaction orders and asserts the final state.

## Projection and snapshot closure

Migration 042 now requires cxxprobe questions and snapshots to remain
`question_type='code'`. A candidate projection cannot bind until PostgreSQL
proves that:

- the selected projection, bundle, question, contest, bundle digest, and
  projection digest are the same identity;
- actual child asset count equals the declared `asset_count`; and
- declared `total_bytes` equals statement bytes, optional starter bytes, and
  the sum of all asset bytes.

The binding trigger locks the projection row before counting assets. Asset FK
checks use the same referenced row, so concurrent binding and asset insertion
cannot both cross the freeze boundary. After a question or snapshot selects a
projection, a new asset insert is rejected.

Session-question insertion now requires an exact copy of the selected question's
engine identity and all candidate-visible display metadata. The trigger locks
the question row `FOR SHARE`, preventing a snapshot from racing organizer
mutation. Existing snapshot update/delete/truncate immutability remains in
force, while deletion of the owning session still performs the intended
database-owned cascade.

All contest-question insert/update/delete operations are now DRAFT-only at the
database boundary, and a question UUID's `contest_id` is permanently immutable,
so moving a row cannot remove it from a published contest by targeting a DRAFT
one. A published cxxprobe contest also cannot return from a non-DRAFT state to
DRAFT and reopen its frozen projection identity.

## Permanent opt-in test harness

`internal/db/migration_postgres_integration_test.go` is guarded by the
`postgres_integration` build tag. It requires both:

```text
AMS_TEST_DATABASE_URL
AMS_TEST_DATABASE_DISPOSABLE=1
```

The supplied role must be allowed to create and drop databases. Each test
creates a cryptographically suffixed database named
`ams_migration_test_<suffix>` and cleanup drops only that exact validated name.
The supplied admin database itself is never dropped. The test refuses to run
without the explicit disposable acknowledgement. The Go README contains the
portable command and a prohibition on production, staging, shared-development,
or Cloud SQL targets.

The suite covers:

- fresh 001–042 application and exact tracking-row count;
- recorded-039 upgrade compatibility repair in migration 042;
- idempotent rerun;
- two simultaneous production migration runners;
- real `pgcrypto`, digest, FK, check, and trigger execution;
- valid statement/starter/asset projection persistence;
- valid, ready partial indexes for both projection-binding lookup paths;
- asset-count and total-byte closure before binding;
- late-asset rejection after binding;
- cxxprobe code-only enforcement;
- DRAFT-only question mutation and cxxprobe DRAFT-regression rejection;
- immutable contest scope, including published-to-DRAFT move rejection;
- exact session snapshot insertion and mismatch rejection;
- direct snapshot immutability and owning-session cascade;
- both binding/status transaction orders;
- both projection-binding/asset-insert transaction orders;
- migration-041 historical-scope preflight failure and complete rollback; and
- migration-042 existing-cxxprobe-binding preflight failure and complete
  rollback.

## Remaining database and operational gates

Phase 2f does not claim the following are complete:

1. Identify the exact Cloud SQL PostgreSQL major from deployment state and run
   this suite against a disposable instance of that exact major and extension
   set.
2. Exercise the production migration role's actual CREATE EXTENSION, DDL,
   trigger, and advisory-lock permissions.
3. Run realistic legacy upgrade-volume/load timing with explicit lock and
   statement timeout policy. The runner still tracks filenames without SQL
   checksums and has no down migrations.
4. Decide and test one-way upload/import lifecycle transitions; direct SQL can
   still rewrite both sides of a deferred pair consistently.
5. Decide whether immutable validated bundles/projections intentionally block
   contest/question/organization deletion and expose a product-safe archive or
   conflict response instead of a generic handler error.
6. Define a compare-and-swap policy if two different valid bundle imports race
   to bind the same DRAFT question. Current repository locking serializes them,
   but the later transaction can deliberately select the later revision.
7. Keep the Go canonical projection digest authoritative. PostgreSQL validates
   every public file digest and closes asset counts/bytes, but does not
   independently reconstruct the canonical JSON projection SHA-256.

The next implementation gate is staging object-storage qualification:
generation-pinned quarantine reads, create-only canonical publication,
corrupt/collision/private-file adversarial cases, and authenticated projection
asset delivery. The exact deployed PostgreSQL-major run should be completed in
parallel or before any production migration rollout.

Phase 2f therefore completes representative real-PostgreSQL schema and
concurrency qualification. It does not authorize production migration or close
staging object-storage, cross-platform desktop, or Phase 3 judging gates.
