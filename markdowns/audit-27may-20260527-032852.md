# AMS Access App Audit

Audit timestamp: 2026-05-27T03:28:52+05:30  
Context updated: 2026-05-27 after platform/admin direction clarification  
Roles: Principal engineer synthesis, senior engineer subagent review, low-latency checker subagent review  
Scope: `ams-access` Tauri shell, Next.js web app, Rust platform modules, shared markdown context, legal pages, current local implementation notes, and the updated external-platform direction shared by the team.

## Updated Platform Context

The external platform direction matters for this audit. `ams-access` should be treated as the secure contestant shell, while `contest-web` owns the browser/admin product surface.

- `contest-web` will include the admin dashboard for contest setup and problem authoring.
- Admin problem authoring is expected to resemble Polygon/Codeforces workflows: statements, examples, testcase assets, validators, generators, checkers, and tester/validator tooling.
- Those problems/questions should sync into `ams-access` through backend APIs. The desktop shell should not own authoring.
- The backend is currently understood to be on Vercel, but the target direction is GCP using available credits.
- Likely GCP building blocks: Cloud Run for Go services, Cloud SQL or Postgres-compatible DB, Cloud Storage buckets for screenshots/submissions/testcases/logs, Pub/Sub or Cloud Tasks for durable submission jobs, worker services for judging, Secret Manager, Artifact Registry, and Cloud Logging.
- The desktop shell should stay provider-agnostic. It should know stable API contracts, auth/session tokens, and signed upload URLs, not whether the backend is Vercel, GCP, or another provider.

## Executive Summary

AMS Access has a strong product direction: a dedicated desktop shell for contests where normal browser delivery is not enough. The monorepo split is sensible, the native Rust surface already exposes meaningful platform checks, and the web UI is broad enough to cover login, hub, readiness, onboarding, contest, support, diagnostics, and legal pages.

The principal concern is that the product currently looks more authoritative than it is. Several critical security paths are optimistic, React-driven, or allow warning-and-continue behavior. The next phase should reduce polish work and concentrate on enforcement boundaries, release hardening, session authenticity, telemetry durability, measured latency, and a stable API contract with the external GCP-bound platform.

Recommended release posture: alpha or controlled pilot only. Do not present it as a high-stakes lockdown client until the enforcement profile, auth, recovery, CSP, and telemetry story are tightened.

- Clear repo architecture:
  - `apps/web`: Next.js 15 static-export contestant UI.
  - `apps/desktop`: Tauri shell and command bridge.
  - `packages/platform-rs`: platform-specific Linux/Windows/macOS lockdown modules.
  - `packages/core-rs`: exam state types and state-machine concepts.
  - `packages/api-client`: shared web-to-Tauri invoke boundary.
- Real native capabilities already exist:
  - Linux process scanning through `/proc`.
  - Linux virtualization and display/session checks.
  - Linux GNOME keyboard shortcut mutation with crash recovery.
  - Windows process scanning through `tasklist`.
  - Windows low-level keyboard hook and sleep prevention.
  - Native TCP reachability checks.
  - Local violation log and face-image save command.
- Product surface is coherent:
  - Contestant hub with sessions, invite code, readiness, settings, diagnostics, and security logs.
  - Onboarding covers a 15-stage pre-session flow.
  - Contest page has editor, preview, heartbeat, save, submit, proctor checks, and support incident modal.
  - Privacy, terms, and license pages now exist and disclose several implementation limits.
- The visual system is memorable and consistent for a secure desktop-shell product.

## Principal Findings

### 1. Security Policy Is Not Yet the Source of Truth

The most important gap is architectural: React components currently orchestrate security decisions through timers, local state, and imperative Tauri calls. `core-rs` owns state-machine concepts, but the effective policy is spread across UI code.

Risk:

- A UI bypass, bug, or inconsistent component state can decide whether a contestant proceeds.
- Different surfaces can disagree about readiness.
- It is hard to prove which checks were required, passed, bypassed, or waived.

How to improve:

- Define a session policy model in `core-rs`, for example:
  - required checks
  - optional checks
  - blocking severity
  - organizer override capability
  - failure reason codes
  - recovery actions
- Expose one typed Tauri command such as `evaluate_session_readiness(policy, contest, device_state)`.
- Let React render the result and request rescans, but not decide if a failed VM, camera, mic, process scan, network check, or keyboard hook is allowed to continue.
- Add an immutable readiness report object that is attached to session start.

Priority: P0.

### 2. Auth and Session Integrity Are Demo-Grade

The current app relies on local email state and demo credentials. Active session recovery is local-storage based. Backend calls are present, but there is no enforced JWT/session-token boundary in this repo.

Risk:

- A local user can spoof identity context.
- Session recovery can become detached from backend trust.
- Contest entry can happen without a strongly validated user, device, and contest binding.

How to improve:

- Replace local email identity with backend-issued JWTs.
- Store tokens in a safer desktop-managed store, not ordinary browser localStorage.
- Bind active session to user ID, contest ID, device fingerprint, client version, and readiness report hash.
- Require backend validation before onboarding and before contest route entry.
- Make logout clear all AMS local state, not only `ams_user_email`.
- Keep the token/session contract cloud-neutral so the desktop client does not care whether the API is currently on Vercel or later on GCP.

Priority: P0.

### 3. Tauri Release Hardening Is Incomplete

Current config has `withGlobalTauri: true` and `csp: null`. This is convenient for development but too permissive for a security shell. Linux WebKit permissions are auto-allowed broadly.

Risk:

- If web content is compromised, the exposed bridge is more powerful than necessary.
- The contest preview/editor and external links need strict origin and navigation policy.
- Broad permission auto-allow makes media more reliable but weakens least-privilege posture.

How to improve:

- Add a strict CSP in `apps/desktop/src-tauri/tauri.conf.json`.
- Remove global Tauri exposure where possible and use explicit capabilities.
- Disable devtools and any debug-only affordances for release builds.
- Intercept navigation and permit only configured AMS origins plus local static assets.
- Make permission handling explicit by command/scope instead of auto-allowing all WebKit requests.
- Add a release-config check script that fails builds when CSP/devtools/global bridge settings are unsafe.

Priority: P0.

### 4. Lockdown Claims Need Sharper Boundaries

The app detects and blocks some things, but not all labels map to enforcement. VM, camera, mic, keyboard, multi-monitor, and restricted-process failures can still warn-and-continue in some flows. Network lockdown exists but is not wired into the main onboarding/contest launch path.

Risk:

- The UI can overstate security.
- Contestants may enter with failed checks.
- Organizers may assume stronger guarantees than the shell provides.

How to improve:

- Create named enforcement profiles:
  - `practice`: warn-only
  - `internal_pilot`: warn plus report
  - `strict_contest`: block on required failures
- Wire `enable_network_lockdown` and `disable_network_lockdown` into strict contest lifecycle.
- Add a recovery screen for firewall state that can run restore actions after a crash.
- Make process scanning actionable:
  - detect
  - show exact app
  - request close
  - optionally kill where legally/operationally acceptable
  - monitor relaunch
- Stop labeling unsupported platform controls as active.
- Document that Windows hooks cannot block secure attention paths like Ctrl+Alt+Del.

Priority: P0/P1.

### 5. Telemetry and Incidents Are Not Durable Enough

Violation records are in memory. Support incident submission is best-effort. Some planned backend sync is not implemented here.

Risk:

- A crash loses key integrity data.
- Support reports can appear sent but be dropped.
- Disputes lack reliable evidence.

How to improve:

- Add a local append-only event store with session ID, monotonic sequence, timestamps, and signature/HMAC when credentials exist.
- Batch and retry uploads with acknowledgement tracking.
- Flush violation logs before submit and periodically during contest.
- Make support incident status reflect actual backend success/failure.
- Add admin-visible event categories and severity levels.
- Use signed upload URLs for bulky artifacts such as screenshots, face/proctoring captures, diagnostics, and submissions. In the current target this likely maps to GCP Cloud Storage, but `ams-access` should only see the signed URL contract.

Priority: P1.

### 6. Privacy and Compliance Are Improved but Need Product Decisions

The legal pages now disclose local face snapshots, network probes, local storage limits, and release-notice caveats. Production still needs a policy decision layer.

Risk:

- Biometric/media handling is high risk.
- Organizer/controller roles are not fully defined.
- Retention schedules are not enforceable from the app.

How to improve:

- Add local face snapshot cleanup or encryption.
- Add a clear "clear all AMS local data" action.
- Define retention:
  - local snapshots
  - local active-session cache
  - violations
  - support incidents
  - submissions
  - audit logs
- Generate exact OSS notices during release.
- Add organizer-facing privacy/config documentation.
- Ensure `contest-web` admin settings expose retention choices for screenshots, submissions, logs, and proctoring artifacts, while `ams-access` renders and obeys the resulting policy.

Priority: P1.

## Low-Latency Findings

### Startup and Build Latency

Current risks:

- `predev` and `prebuild` always run `setup-mediapipe.mjs`.
- Tauri dev inherits the web predev path.
- Static export and ML assets make the app heavier than expected.
- Reported local sizes from checker pass:
  - `apps/web/out`: about 38 MB
  - `.next`: about 448 MB
  - `public/mediapipe`: about 36 MB

How to improve:

- Make MediaPipe setup idempotent and cheap:
  - skip copy when hashes match
  - skip model checks unless the active implementation requires MediaPipe
  - split `setup-mediapipe` from normal dev startup
- Add size budgets in CI for `out`, JS chunks, and ML assets.
- Audit whether MediaPipe assets are actually used, because onboarding appears to rely heavily on TFJS BlazeFace.

Priority: P1.

### Runtime UI Latency

Current risks:

- Contest countdown updates can rerender the whole contest client every second.
- Scheduled contest cards each run their own one-second interval.
- Editor is controlled and iframe preview remounts after debounced edits.
- Face/audio loops update state at high frequency.

How to improve:

- Move countdowns into tiny memoized leaf components.
- Use one shared ticker for scheduled contest cards.
- Keep camera/canvas loop data out of React state unless UI labels actually change.
- Throttle face/audio state updates to 4-10 Hz.
- Replace iframe `key={previewSrc}` remount with cheaper `srcDoc` updates or an explicit Run Preview action.
- Track keystroke-to-preview latency and long tasks while typing.

Priority: P1/P2.

### Native Probe Latency

Current risks:

- `check_network_stability` runs three sequential TCP connects with three-second timeouts, so worst case is about nine seconds.
- Home readiness performs native checks mostly sequentially; settings does a better parallel `Promise.all`.
- Windows `systeminfo`, `tasklist`, Linux `/proc`, and firewall commands can vary widely in latency.
- Onboarding probes `supabase.com` and can fall back to Google instead of consistently probing the configured API host.

How to improve:

- Parallelize Home readiness checks like Settings.
- Add UI-level abort/timeouts and partial readiness states.
- Run network samples in parallel or use staged timeouts:
  - 800 ms first fast path
  - 2 s fallback
  - no more than 3 s total for dashboard checks
- Probe the configured AMS API host, not hardcoded `supabase.com`.
- Record duration for each native command and show p50/p95/p99 in diagnostics.

Priority: P1.

### Media and ML Cost

Current risks:

- TFJS CPU backend and BlazeFace import/load cost can be high on low-end machines.
- Inference runs around every 120 ms while canvas draws every animation frame.
- `toDataURL("image/png")` is synchronous and can block the UI thread.

How to improve:

- Benchmark model import time, first inference, steady FPS, CPU, memory, and dropped frames.
- Consider WebGL or WASM backend where supported by the Tauri webview.
- Use `canvas.toBlob` instead of synchronous `toDataURL` for face snapshot capture.
- Gate face scanning behind explicit readiness stage, not early page load.

Priority: P2.

## Senior Engineer Findings

The senior engineer review agreed with the principal assessment: AMS Access is a promising alpha-grade shell, not production lockdown. The biggest gap is not visual quality; it is trust boundaries.

Key senior-review points incorporated:

- `core-rs` should be more than a state model; it should own policy.
- `@ams/api-client` should become a typed command contract, not a raw invoke export.
- Bypass/warn behavior should be controlled by organizer policy.
- Network lockdown and violation upload need lifecycle integration.
- Legal pages are a good start but need generated OSS notices and true retention controls.
- Native lockdown should be reported honestly per OS and capability.

## Improvement Roadmap

### Phase 0: Measurement and Truthfulness

Goal: make the app observable and stop overclaiming.

Work:

- Add `performance.mark` and native timing wrappers for:
  - `app_start`
  - `first_paint`
  - `home_ready`
  - `readiness_done`
  - each onboarding stage duration
  - `contest_loaded`
  - `preview_update_ms`
  - every Tauri command duration
- Add diagnostics display/export for those timings.
- Rename labels that imply unsupported full lockdown.
- Remove strict-sounding copy from warn-only flows.

Success criteria:

- Every readiness check has duration, result, source, and severity.
- UI copy distinguishes blocked, warning, unsupported, and simulated states.

### Phase 1: Security Contract

Goal: one policy engine decides session entry.

Work:

- Define `SessionPolicy`, `ReadinessCheck`, `ReadinessReport`, and `EnforcementDecision` in `core-rs`.
- Implement Tauri commands:
  - `collect_device_state`
  - `evaluate_readiness`
  - `start_secure_session`
  - `end_secure_session`
- Move warning/bypass decisions out of React.
- Add backend validation before route entry.
- Define API payload contracts for contest/question sync from the admin platform into `ams-access`.
- Keep problem payloads compatible with Polygon-style assets while sending only contestant-needed fields to the desktop shell.

Success criteria:

- React cannot enter strict contest mode when policy returns blocked.
- Every bypass is explicit, policy-governed, and logged.

### Phase 2: Release Hardening

Goal: make the desktop shell safe enough for pilots.

Work:

- Add strict CSP.
- Remove or minimize global Tauri bridge.
- Disable release devtools.
- Intercept navigation.
- Add origin allowlist.
- Harden media permissions.
- Add release config CI check.

Success criteria:

- Release build fails if CSP is null, global bridge is enabled without justification, or devtools are enabled.
- External navigation cannot escape the approved origin set.

### Phase 3: Auth and Durable Telemetry

Goal: backend trust and recoverable evidence against the Vercel-now, GCP-target platform.

Work:

- Replace local demo auth with real token flow.
- Store active session securely.
- Sign or hash readiness reports.
- Add local durable violation queue.
- Upload violation batches with retry and ack.
- Make support incidents real, not best-effort.
- Route large artifacts through signed upload URLs and durable queues. On GCP, use Cloud Storage for artifacts and Pub/Sub or Cloud Tasks for async submission/telemetry jobs.

Success criteria:

- Restart/crash does not lose unuploaded violation events.
- Contest entry requires valid backend session.
- Support modal reports actual delivery state.

### Phase 4: Lockdown Lifecycle

Goal: safe mutation and reliable restoration.

Work:

- Wire network lockdown into strict contest start/end.
- Add firewall privilege/elevation UX.
- Add restore/recovery screen for leftover firewall or keyboard state.
- Add per-platform capability probes.
- Decide whether process kill is allowed; if yes, implement with logs and restore guidance.

Success criteria:

- Lockdown state can be inspected and restored from the UI.
- Crash recovery covers keyboard and network state clearly.
- Unsupported OS features are not shown as active.

### Phase 4B: Admin/Problem Sync Contract

Goal: make `ams-access` consume contest-web/admin-authored problems without becoming an admin product.

Work:

- Define a compact `ContestBundle` API for the shell:
  - contest metadata
  - timing and eligibility
  - allowed languages/question types
  - proctoring policy
  - lockdown policy
  - question statements and starter files
  - submission endpoint metadata
- Keep validator/generator/checker internals on the backend/admin side unless the contestant shell needs a safe preview.
- Add versioning for problem payloads so old desktop clients can be blocked or given compatible fields.
- Add checksum/signature fields for contest bundles to prevent tampering.
- Add admin preview mode in `contest-web` that renders exactly what `ams-access` will receive.

Success criteria:

- A problem authored in `contest-web` can be reviewed, approved, published, synced, opened in `ams-access`, submitted, judged, and reviewed without manual data copying.
- `ams-access` never needs direct bucket credentials or admin-only problem assets.

Priority: P1.

### Phase 5: Latency and Asset Diet

Goal: keep the shell fast on real contestant machines.

Work:

- Parallelize Home readiness checks.
- Shorten network probe worst-case.
- Reduce MediaPipe/ML asset footprint.
- Isolate one-second timers.
- Throttle camera/audio React updates.
- Optimize preview iframe updates.

Success criteria:

- Home readiness p95 under 3 seconds on healthy network.
- Failed network readiness p95 under 4 seconds.
- Contest editor keystroke-to-paint p95 under 100 ms.
- Onboarding face scan maintains target FPS on low-end test devices.

## Final Principal Recommendation

Treat AMS Access as a strong alpha foundation. The right next move is not another visual pass; it is a trust pass.

Build a single policy engine, harden the Tauri shell, replace demo auth, make telemetry durable, define the admin/problem sync contract, and measure the slow paths. Once those are in place, the existing UI and native modules can become a credible secure contest client rather than a polished shell around partial enforcement.
