# AMS Access Codebase Comprehensive Audit - 01-06-2026

This document is the "single source of truth" for the `ams-access` codebase. It provides an exhaustive, granular mapping of all folder structures, file-specific responsibilities, cross-module interconnections, API call sequences, data persistence locations, and OS-specific service integrations for both the desktop shell and the web frontend.

---

## 1. High-Level Architecture

The AMS Access application is a highly secure, proctored examination environment operating in a strict lockdown mode. It utilizes a hybrid architecture:

- **Tauri (Rust)**: The secure, native OS-level desktop shell (`apps/desktop/`). It acts as a hardened kernel, enforcing network rules, process monitoring, and keyboard interception.
- **Next.js (React/TypeScript)**: The client-facing frontend (`apps/web/`). It is a static export single-page application loaded inside the Tauri WebView, managing the contest interface, onboarding flows, and UI/UX.

---

## 2. Exhaustive Directory and File Map

### A. The Native Shell (`apps/desktop/`)

The native shell controls the OS environment and communicates via the Tauri IPC bridge.

- **`src-tauri/Cargo.toml`**: Configures the Tauri app dependencies, importing the local `core-rs` and `platform-rs` workspace packages.
- **`src-tauri/tauri.conf.json`**: Configures the Tauri build, specifying the window parameters (1280x800, centered), `frontendDist` (`../../web/out`), and bundle targets (`deb`, `rpm`, `appimage`).
- **`src-tauri/src/main.rs`**: The entry binary that boots the Tauri application.
- **`src-tauri/src/lib.rs`**: The nexus of the native backend.
  - **Responsibilities**: Registers Tauri commands, sets up WebView hooks (automatically granting camera/microphone permissions via `req.allow()`), manages the main window state, and maintains in-memory violation logs via `OnceLock<Mutex<Vec<ViolationEntry>>>`.
  - **Exposed APIs**: `collect_device_state`, `evaluate_session_readiness`, `start_secure_session`, `lock_desktop`, `unlock_desktop`, `save_face_image`, `scan_processes`, `detect_virtualization`, `log_violation`.

### B. The Frontend Web App (`apps/web/`)

The Next.js React application served inside the Tauri WebView.

- **`next.config.mjs`**: Configures Next.js for a pure static export (`output: "export"`) compatible with Tauri, disabling server features and image optimization.
- **`src/app/globals.css`**: Defines the rigorous design system. Uses a Tailwind v4 `@theme` block. Enforces the strict "Obsidian Dark" aesthetic (#0F0F0F base, #a855f7 accent).
- **`src/constants/storage-keys.ts`**: Centralizes `localStorage` keys to prevent typos (e.g., `ams_active_session`, `ams_user_email`, `ams_theme`).
- **`src/lib/api-base.ts`**: Resolves the remote REST API base URL. Defaults to `https://ams-api-test-pdtqgdjqia-uc.a.run.app` in production.
- **`src/app/layout.tsx`**: Injects `Inter` and `JetBrains Mono` fonts and standardizes the dark HTML body.
- **`src/app/page.tsx`**: The login page.
- **`src/app/home/page.tsx`**: The pre-contest dashboard. Fetches contest invitations and triggers the pre-flight checks before navigating to onboarding.
- **`src/app/session/onboarding/page.tsx`**: The massive 15-stage onboarding sequence.
  - **Responsibilities**: Orchestrates the strict readiness funnel.
  - **Stages**:
    1-5: Isolation, Fullscreen, Monitor, Keyboard, Env check.
    6: Restricted App check (`scan_processes` API).
    7: VM Detection (`detect_virtualization` API).
    8: Camera Setup.
    9-10: Face Calibration (TensorFlow.js BlazeFace) & Verification.
    11-14: Audio, Network, Integrity, Lock-in.
    15: Wait for contest start.
  - **Cross-module connection**: Calls the remote `/sessions` API to provision the backend session ID before locking the system and routing to the contest.
- **`src/app/session/contest/client.tsx`**: The actual examination interface.
  - **Responsibilities**: Manages the multi-pane layout (HTML/CSS/JS editor), continuous proctoring (camera stream handling, periodic process scanning every 5s), and network heartbeats.

### C. Workspace Packages (`packages/`)

- **`packages/api-client/src/index.ts`**: The TypeScript bridge. Exposes friendly JavaScript async wrappers for the raw Tauri invoke commands (`window.__TAURI__.core.invoke`). Standardizes TypeScript interfaces for `DeviceState`, `SessionPolicy`, and `ReadinessReport`.
- **`packages/core-rs/src/exam/mod.rs`**: Core Rust business logic. Contains definitions for session states and enforcement profiles. Handles the pure evaluation of `DeviceState` against a policy without triggering OS side effects.
- **`packages/platform-rs/src/linux/mod.rs`**: Linux-specific system integration.
  - **Responsibilities**: Process scanning, VM detection, keyboard interception (via GSettings to override WM shortcuts), network lockdown (via `iptables`).
- **`packages/platform-rs/src/windows/mod.rs`**: Windows-specific system integration.
  - **Responsibilities**: Process scanning, VM detection (via Registry), keyboard interception (via `WH_KEYBOARD_LL`), network lockdown (via `netsh`).

## 3. Cross-Module Interconnections & API Call Sequences

The application utilizes two separate communication channels: the **Local Tauri IPC** (Frontend <-> Native Shell) and the **Remote REST API** (Frontend <-> Cloud Backend).

### A. The Onboarding / Readiness Sequence (Local & Remote)

1. Frontend `onboarding/page.tsx` runs through stages 1-14.
2. At Stage 6, Frontend invokes Local API: `scan_processes()`. Tauri delegates to `platform-rs`, checking running tasks against blacklisted names (e.g., `obs`, `wireshark`).
3. At Stage 7, Frontend invokes Local API: `detect_virtualization()`.
4. At Stage 9, Frontend invokes Local API: `save_face_image()` during the TensorFlow JS scan.
5. At Stage 15 (Completion), Frontend evaluates the Contest Start Time metadata.
6. Frontend executes a Remote API POST to `https://ams-api-test-pdtqgdjqia-uc.a.run.app/sessions` containing the candidate email and contest ID.
7. If the remote API succeeds, the session ID is returned.
8. Frontend invokes Local API: `start_secure_session()`. The Tauri shell enforces window always-on-top, fullscreen, and initiates `enable_keyboard_intercept` in `platform-rs`.
9. Frontend routes to `/session/contest`.

### B. The Contest Lifecycle & Continuous Monitoring

1. Once in `contest/client.tsx`, Frontend establishes a `MediaStream` and continually draws video frames to monitor the user's face.
2. **Heartbeat Sequence**: Frontend executes a Remote API POST to `/sessions/{id}/heartbeat` every 60 seconds to signal to the cloud that the candidate is active.
3. **Continuous Scanning**: Frontend runs an interval every 5 seconds invoking Local API: `scan_processes()`.
4. If a restricted app is found, Frontend immediately triggers Local API `log_violation` and displays a strict overlay dialog. The system begins a "grace period" countdown before fully blocking the interface.

## 4. Data Persistence & State Locations

### Frontend Storage

- **Browser `localStorage`**: Managed via keys in `storage-keys.ts`.
  - `ams_theme`: Stores the UI theme preference.
  - `ams_user_email`: The authenticated user's email.
  - `ams_active_session`: A JSON object holding `{ id, contest_id, updated_at }` mapping to the remote backend.
  - `ams_device_id`: A persistent UUID generated on the client.

### Backend State

- **Rust In-Memory Mutex (`OnceLock`)**: The Tauri backend holds the active session state, security profile variables, and a running array of `ViolationEntry` objects. This data is purposely volatile and lost on process death.
- **Local File System**:
  - Temporary face captures are written to `/tmp/ams_faces/` (Linux) or `%TEMP%\ams_faces\` (Windows). Base64 image data sent over IPC is decoded and stored here for potential audit upload.

## 5. OS-Specific Service Integrations

The `ams-access` native layer leverages distinct OS primitives to enforce the "kernel-level" environment:

### Linux (`platform-rs/src/linux/mod.rs`)

- **Process Management**: Reads `/proc` to map running PIDs.
- **Keyboard/Input Hooks**: Modifies `GSettings` (dconf) schemas dynamically to override or disable desktop environment shortcuts (e.g., Alt-Tab, Super key) for Wayland/X11 compatibility.
- **Network Lockdown**: Executes underlying shell commands for `iptables` to flush existing rules and enforce a strict whitelist.
- **Webview Engine**: Leverages `webkit2gtk` for rendering the Next.js frontend.

### Windows (`platform-rs/src/windows/mod.rs`)

- **Process Management**: Uses `CreateToolhelp32Snapshot` via the Windows API to parse running executable names.
- **Keyboard/Input Hooks**: Installs a global `WH_KEYBOARD_LL` low-level hook via `SetWindowsHookEx` to intercept and discard forbidden key combinations.
- **Virtualization Detection**: Probes the Windows Registry (e.g., `HKLM\HARDWARE\DESCRIPTION\System`) for known hypervisor strings.
- **Network Lockdown**: Uses `netsh advfirewall` rules to block outbound traffic except for designated whitelisted IP ranges.
- **Webview Engine**: Leverages `WebView2` (Edge Chromium).

## 6. Technical Constraints & Known Behaviors

- **Rigid Aesthetics**: The frontend avoids soft UI features. Drop shadows, blurs, and border radii are aggressively minimized in favor of stark grids, 1px hairlines, and monospace typography.
- **Grace Periods**: Violations like face detection loss or restricted app detection trigger a UI "soft block" before enforcing a hard penalty, giving the user 5 to 15 seconds to rectify the anomaly.
- **Emergency Abort**: A hidden global shortcut (`Ctrl+Shift+Q`) is bound in the onboarding flow to forcefully disengage the Tauri desktop locks and drop back to the dashboard if a catastrophic UI loop occurs.

## 7. Cloud Synchronization & External Organization Mapping

The `ams-access` native application is the strictly enforced execution environment for exams configured upstream on the cloud dashboard (`amsaccess.com/org`). Understanding this split is critical for API integration.

### Organization & Question Lifecycle

1. **Creation (Cloud)**: Administrators and proctors log into `amsaccess.com/org` (an entirely separate web application) to create contests, configure questions, set time limits, and define security policies.
2. **Synchronization (API)**: When a candidate launches the AMS Access desktop app, the frontend fetches the contest metadata via the `API_URL` (`https://ams-api-test-pdtqgdjqia-uc.a.run.app`).
3. **Execution (App)**:
   - Questions authored in the cloud sync directly to the `apps/web/src/app/session/contest/client.tsx` interface.
   - The desktop app handles code execution and interface management completely locally within its sandboxed WebView, rather than pushing every keystroke over the network.
   - Code submissions, snapshots, and violation reports (like Face Recognition failures or restricted app detection) are continuously synced back to the cloud via the `/sessions/{id}/heartbeat` and similar telemetry endpoints.

### Key API Endpoints & Sync Mechanisms to Keep in Mind

- **`GET /contests/{id}`**: Called by `home/page.tsx` and onboarding to fetch contest metadata, ensuring the local app enforces the exact start and end times configured in the org dashboard.
- **`POST /sessions`**: Maps the candidate's email and device ID to the contest, returning a session ID that tracks the entire attempt on the backend.
- **`POST /sessions/{id}/heartbeat`**: The most critical sync point during the contest. Occurring every 60 seconds, this guarantees the org dashboard sees real-time status (Active, Warning, Terminated) of the candidate.
- **Violation Logging (Local to Cloud)**: Currently, `log_violation` is a Tauri command that keeps state locally. Future integration expects these local logs to batch-sync to the cloud so proctors on `amsaccess.com/org` can view live infractions.

## 8. Golang Backend & Remote Execution Syncs

While the `ams-access` native app is built on Rust (Tauri) and React (Next.js), it interfaces heavily with external microservices—typically written in **Golang**—to handle high-concurrency tasks, such as code execution and telemetry aggregation.

### Code Execution Syncs

- **Remote Evaluation Pipelines**: When a candidate writes code (e.g., in the web-based IDE in `/session/contest/client.tsx`) and submits it, the request is dispatched to a Golang-based evaluation runner.
- **Payload Structure**: The `ams-access` frontend gathers the raw code string, language metadata, and contest IDs, sending them via POST requests to the execution API.
- **Real-Time Polling vs WebSockets**: The Golang execution service typically runs user code in isolated containers (e.g., Docker/gVisor). The frontend must handle latency and asynchronous polling (or WebSocket events) to update the UI with compiler outputs, stack traces, or test case successes without blocking the main React render thread.

### Telemetry & Heartbeat Handling

- **High-Throughput Golang Ingestion**: The `/sessions/{id}/heartbeat` endpoint is designed to be highly concurrent. The Golang backend processes thousands of simultaneous `ams-access` clients sending their 60-second pings, face detection statuses, and process violation logs.
- **Data Consistency**: The local `ams-access` app operates on a "best effort" delivery for logs. If the network drops (despite the iptables lockdown), the Rust backend or React frontend must queue the telemetry and sync it to the Golang backend once the connection is restored, ensuring proctors on `amsaccess.com/org` eventually receive a complete, chronological audit trail.

## 9. Key AI Models & External Integrations

To enforce examination integrity locally without relying on heavy cloud inference (which introduces latency and privacy concerns), the AMS Access client embeds specialized machine learning models and hooks directly into the frontend.

### TensorFlow.js & BlazeFace

- **Purpose**: Used for continuous facial detection and presence verification during the onboarding phase and the live contest.
- **Implementation in App**:
  - The `@tensorflow/tfjs-core` and `@tensorflow-models/blazeface` packages are loaded dynamically during Stage 9 of onboarding (`Stage9_FaceCalibration`).
  - The model runs entirely client-side using the `cpu` backend to ensure compatibility across machines without requiring dedicated GPUs.
  - It captures a `MediaStream` from the user's webcam, drawing the frames to a hidden HTML canvas at roughly ~8 FPS to detect the face's bounding box and landmarks (eyes, nose, mouth, ears).
- **Evaluation Mechanics**: The client uses the raw landmark coordinates from BlazeFace to calculate **pose estimation** (yaw, pitch, roll). This ensures the candidate is actually looking at the screen rather than glancing away or using a printed photo.
- **Action Triggers**: If the BlazeFace model fails to detect a face for a grace period, or if the pose estimation determines the user is looking away, it triggers a UI "soft block" in `contest/client.tsx`. This logs a `face_away` telemetry event to the backend.

### System-Level Security Integrations

- **GSettings (Linux) / SetWindowsHookEx (Windows)**: Used heavily by the `platform-rs` package to intercept keystrokes at a lower level than the browser's JavaScript event loop, effectively blocking OS-level multitasking shortcuts.
- **Network Firewalls (iptables / netsh)**: Integrated directly by Rust to modify the host machine's firewall rules dynamically when a session starts, creating a "default-deny" outbound rule exception only for the `amsaccess.com` API endpoints.

## 10. Critical UI/UX Testing Areas & Cross-Platform Checklist

As the platform expands to include complex assessment types—such as live orderbook simulations or high-frequency data tables—the contest UI requires meticulous performance profiling and cross-platform validation to prevent UI jank while heavy native processes run in the background.

### High-Priority UI/UX Optimization Areas

- **Complex Question Rendering**: Components rendering dense data (e.g., orderbook bids/asks, financial simulations) must use virtualization (like `react-window`) to prevent DOM bloat.
- **Background Model Throttling**: The TensorFlow JS face scanner runs at ~8 FPS. It is crucial to ensure this `requestAnimationFrame` loop does not starve React's main thread during rapid user typing or when an orderbook component re-renders.
- **Strict Monochromatic Grid**: Complex visual components must adhere to the global CSS strictures (e.g., #0F0F0F backgrounds, 1px hairlines). No gradients, blur filters, or heavy transitions should be introduced that could impact WebGL/Canvas rendering performance.

### Cross-Platform Testing Checklist

#### Windows 10/11

- [ ] **Keyboard Interception**: Verify `SetWindowsHookEx` successfully blocks `Alt+Tab`, `Win` key, and `Ctrl+Esc`.
- [ ] **Process Scanning**: Ensure `CreateToolhelp32Snapshot` accurately detects `obs64.exe`, `discord.exe`, and `Taskmgr.exe`.
- [ ] **Firewall Execution**: Validate that the app has sufficient privileges to invoke `netsh advfirewall` without triggering a UAC prompt that crashes the fullscreen state.
- [ ] **WebView2 Rendering**: Test complex orderbook components in WebView2 for layout regressions or stuttering.

#### Linux (X11 / Wayland)

- [ ] **GSettings Override**: Confirm that Wayland-compatible desktop environments correctly accept `gsettings` overrides for multitasking shortcuts (e.g., Gnome Super key).
- [ ] **Process Scanning**: Verify parsing of `/proc` successfully flags restricted apps like `wireshark` or `teamviewer`.
- [ ] **iptables Routing**: Ensure the app safely applies and flushes `iptables` rules. Test recovery in the event of an unexpected app crash.
- [ ] **Webkit2GTK Performance**: Validate that TensorFlow.js CPU processing does not severely throttle Webkit2GTK rendering on lower-end Linux laptops.

#### macOS (Apple Silicon / Intel)

- [ ] **Accessibility Permissions**: Ensure the app elegantly requests Accessibility API permissions for system-level key blocking (EventTap).
- [ ] **Process Scanning**: Validate `NSWorkspace` or `ps` parsing correctly identifies restricted macOS apps.
- [ ] **Packet Filter (pf)**: Verify that macOS network lockdowns using `pf` (Packet Filter) correctly whitelist only `amsaccess.com` and properly revert on session exit.
- [ ] **WKWebView Validation**: Test rendering performance of high-density UI elements (orderbooks) within macOS's native `WKWebView`.
- [ ] **Apple Developer Program ($99 Plan)**: Ensure the application is properly signed and notarized via an active Apple Developer account to prevent macOS Gatekeeper from blocking the native Tauri shell execution on candidate machines.

## 11. Important Syncs to Check Before Proper Launch & Full Pre-Flight Checklist

Before deploying the client to production, the synchronization pipelines between the native application and the Golang/Next.js backends must be rigorously validated to prevent data loss or catastrophic lockouts during a high-stakes exam.

### Critical Pre-Launch Sync Checks

- **Time/NTP Drift Sync**: Ensure the client's local system time accurately syncs against the `amsaccess.com/org` contest start/end times via `GET /contests/{id}`. A skewed local clock could prematurely lock out a candidate.
- **Offline Telemetry Recovery**: Deliberately drop the network connection during an active contest session. Verify that the client caches `face_away` and `restricted_app` violations locally and flushes them successfully to `POST /sessions/{id}/heartbeat` once the connection is restored.
- **State Hydration Sync**: If the Tauri app crashes and is restarted mid-contest, verify that the frontend can fetch the active session state from the backend to instantly drop the user back into the `/session/contest/client.tsx` interface, preserving their unsaved code buffer.

### Full Pre-Launch Checklist

- [ ] **API Endpoint Configuration**: Verify `API_URL` in `api-base.ts` is explicitly pointed to the production cluster (`https://ams-api.a.run.app` or similar) instead of local dev or staging test beds.
- [ ] **Tauri IPC Stability**: Run the full onboarding flow 50+ times to ensure `window.__TAURI__.core.invoke` does not hit unhandled Rust panics (especially during camera acquisition or rapid window state changes).
- [ ] **Code Runner Scalability**: Simulate 5,000+ concurrent clients submitting code compilation payloads to the Golang runner to monitor container spin-up latency and WebSocket broadcast delays.
- [ ] **Strict CSS Compilation**: Verify `globals.css` properly compiles without introducing accidental CSS gradients or soft shadows that violate the strict `#0F0F0F` monochromatic mandate.
- [ ] **Face Detection Degradation**: Test BlazeFace in extremely low light or with a 480p webcam. Ensure the "grace period" correctly triggers a UI warning before issuing a hard violation.
- [ ] **Firewall Rollback**: Force-kill the Tauri process via Task Manager/`htop`. Verify that the OS-level firewall exception (iptables/netsh) correctly expires or flushes, so the candidate's machine regains normal internet access.
- [ ] **Release Builds**: Ensure the final Rust compilation is built using `--release` to strip debug symbols and maximize CPU efficiency for process scanning.
