Full display capture at 5–10fps (not 30fps — storage/bandwidth tradeoff). Periodic screenshots for AI analysis pipeline. Suspicious segments flagged for review.

MUST-HAVE

Block copy-paste from external sources. Track paste events with clipboard content hash. Detect if content entered via paste differs from what was typed.

MUST-HAVE

gVisor or Firecracker MicroVM per submission. 15+ language support. Time and memory limits enforced per testcase. Side-channel prevention (no internet access).

ADVANCED

Focus / tab-switch detection

Page Visibility API + native OS-level foreground window tracking. Log every focus loss with timestamp. Configurable threshold before auto-flagging (3 switches = flag).

ADVANCED

Native agent enumerates running processes every 15s. Blocklist of known cheating tools (TeamViewer, AnyDesk, VMs, Cheat Engine, browser devtools). Configurable by exam creator.

ADVANCED

Track DNS queries during exam. Flag TLDs commonly associated with answer sites (Stack Overflow, GitHub, Chegg). Not blockable without compromising user trust — detect instead.

ADVANCED

Native APIs (Win32 EnumDisplayMonitors, macOS NSScreen.screens) detect secondary screens. Prompt or block if candidate has more monitors than expected.

Keystroke dynamics (dwell time, flight time) as a passive identity signal. Catches cases where someone starts but hands off. Requires enrollment session.

Browser-Based vs Native App — The Critical Decision

This is the most consequential architectural choice you make. It affects security depth, OS permissions, distribution friction, and maintenance burden.

Screen capture prevention Cannot prevent macOS: partial; Win: DRM possible
Multi-display detection No Yes

macOS Gatekeeper friction Low Requires notarization + signing

Recommendation: Build a hybrid. Use a native Electron/Tauri app as the exam shell — it provides the process monitoring, clipboard control, and OS hooks you need. The actual exam content (code editor, MCQ renderer) is a sandboxed web view within the app. This gives you native security depth with web-based content flexibility.

Online vs Offline Proctoring Tradeoffs

Online (AI-assisted) — your recordings are analyzed asynchronously by CV models. Cheaper at scale, no human labor, but higher false-positive rates. Works for mass-hiring (500+ candidates). Candidates need only be told "recorded and reviewed" which sets behavioral expectations.

Live human proctoring — a proctor watches a 1:N grid of candidates in real time. Higher integrity signal, immediate intervention capability. Costs scale linearly with candidates (~1 proctor per 15–30 candidates). Required for high-stakes exams (bar exams, certifications).

For a startup: launch with async AI proctoring, offer live proctoring as a premium SKU routed through a third-party proctoring pool (Proctor U, Honorlock, etc.) via API integration.

Microservices vs Monolith Decision

Don't start with microservices. The overhead of distributed transactions, service discovery, and inter-service auth is enormous at MVP stage. Start with a modular monolith — clean domain boundaries (Exam, User, Submission, Proctor) enforced by module boundaries in code, but deployed as one binary.

Carve out services only when you hit scaling boundaries. The code execution judge is the first to split — it's the highest CPU consumer with different scaling patterns than the web tier. Media ingestion (webcam streams) is the second — it needs SFU-style architecture that doesn't fit the HTTP request/response model.

Realistic extraction order: Monolith → extract Judge Service (week 8) → extract Media Ingestion (week 12) → extract Proctoring AI pipeline (week 20). Everything else can stay in the monolith until you hit actual bottlenecks.

Real-Time Monitoring Pipeline

Every anti-cheat event (tab switch, focus loss, clipboard paste, process detection, gaze deviation) must be:

  1. Timestamped with client-side and server-side timestamps (to detect clock manipulation).
  2. Persisted durably — if the WebSocket drops, events buffer locally and flush on reconnect. Never lose an event.
  3. Correlated with the video timeline so reviewers can seek to the exact moment.
  4. Aggregated into a per-candidate integrity score in near-real-time.
anti-cheat event schema (TypeScript) 
interface ProctoringEvent {
  eventId:       string;        // UUIDv7 — monotonic, time-ordered
  candidateId:   string;
  examSessionId: string;
  eventType:     EventType;     // enum: TAB_SWITCH | FOCUS_LOST | PASTE | PROCESS_DETECTED | ...
  severity:      'low' | 'medium' | 'high';
  clientTs:      number;        // client performance.now() + epoch
  serverTs:      number;        // set by server on receive
  videoOffsetMs: number;        // ms since recording started (correlation key)
  metadata:      Record<string, unknown>;  // type-specific payload
  sequence:      number;        // monotonic counter per session, for gap detection
}

Video/Audio Streaming Architecture

WebRTC (mediasoup SFU) is the right choice for live proctoring. Each candidate's webcam + screen feed goes to a Selective Forwarding Unit (SFU) rather than mesh or MCU. The SFU forwards raw streams to the proctor's browser without transcoding, minimizing latency and server CPU. For async proctoring, you don't need WebRTC at all — use periodic JPEG snapshots (every 5–30s) plus a chunked video upload pipeline (HLS segments every 6s directly to S3).

Critical design: decouple live viewing from storage. The SFU handles real-time, but simultaneously the client sends chunked video segments to a media ingestion endpoint that stores to S3. If the live stream drops, you still have the recordings. These are separate concerns — don't try to record from the SFU; it introduces transcoding latency and a single point of failure.

Bandwidth budget per candidate: Webcam at 720p = ~800 kbps. Screen capture at 5fps = ~200 kbps. Total: ~1 Mbps per candidate. At 10,000 concurrent: 10 Gbps ingress. This is your primary cost driver. Plan TURN server capacity accordingly — assume 20% of candidates are behind symmetric NAT.

Data Flow During an Exam

  1. Pre-exam: Candidate downloads + installs native agent. System check runs (browser, camera, mic, OS version, disk space). Identity verification via ID + face capture. Session token issued, tied to device fingerprint + IP.
  2. Exam start: Encrypted exam package fetched (questions not in plaintext in memory). Webcam + screen recording begins. WebSocket established for real-time events. Judge service pre-warms MicroVM pool for this exam session.
  3. During exam: Every keystroke logged with timestamp (for behavioral analysis). Code submissions go to Judge Service → MicroVM → results returned in <3s. Anti-cheat events stream via WebSocket → Kafka. Video segments chunked to S3 every 6 seconds. Redis stores live session state (answers, timer, event count).
  4. Exam end: Final answers persisted to PostgreSQL. Video segments stitched (async job). AI proctoring pipeline processes full recording. Integrity report generated. ATS webhook fired if configured.

Client Application Design

Native App Architecture (Electron + C++ Native Agent)

Use Tauri (Rust) over Electron if starting fresh. Smaller binary (~5MB vs ~150MB), lower RAM, better security sandbox model. The webview renders your exam UI. A sidecar Rust binary handles OS-level monitoring (process enum, clipboard, screen detection). On Windows, the sidecar needs to run elevated for reliable process enumeration; prompt once at install, not at exam time.

process detection — Windows (Rust / winapi) 
use winapi::um::{tlhelp32::*, handleapi::*};

fn enumerate_processes() -> Vec<String> {
    let mut processes = Vec::new();
    unsafe {
        let snapshot = CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0);
        let mut entry: PROCESSENTRY32W = std::mem::zeroed();
        entry.dwSize = std::mem::size_of::<PROCESSENTRY32W>() as u32;
        
        if Process32FirstW(snapshot, &mut entry) != 0 {
            loop {
                let name = String::from_utf16_lossy(&entry.szExeFile)
                    .trim_matches('\0').to_lowercase();
                processes.push(name);
                if Process32NextW(snapshot, &mut entry) == 0 { break; }
            }
        }
        CloseHandle(snapshot);
    }
    processes
}

macOS-Specific Constraints — This Will Be Your Hardest Platform

macOS enforces strict entitlements for:

  • Screen Recording: Requires explicit user consent in System Settings → Privacy. Your app must declare com.apple.security.screen-capture in entitlements. Sandboxed apps cannot capture displays owned by other apps without user grant. You cannot programmatically grant this — the user must do it manually during setup.
  • Process Enumeration: Post-macOS 11, listing other apps' processes is limited. proc_listallpids() works for PIDs but getting executable paths requires proc_pidpath() which may fail for system processes. You can get meaningful signal for most third-party apps.
  • Accessibility API: Needed for keyboard hooks and window monitoring. Requires user to grant access in System Settings → Privacy → Accessibility. Without this, you cannot detect active application or intercept keyboard events system-wide.
  • Notarization + Hardened Runtime: Required for Gatekeeper. You must sign with a Developer ID, submit to Apple notarization. The hardened runtime disables certain powerful APIs unless you explicitly request entitlement exceptions. This means JIT compilation, DTrace, debugging, certain memory mappings all need explicit entitlement requests — which Apple may reject.
What is impossible on macOS (without MDM): You cannot prevent screen mirroring (AirPlay to Apple TV), cannot block screen recordings made by third-party apps with screen recording permission, cannot force-quit other apps without Root/SIP involvement, and cannot read clipboard content across security contexts if Sandboxed. Accept these limitations and compensate with AI-based behavioral detection.

Screen Sharing Prevention — Reality Check

Windows: Use SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE) to exclude your window from screen capture APIs (including OBS, Teams screenshare, etc.). This is a legitimate Win32 API used by DRM systems. It won't stop phone cameras pointed at the screen.

macOS: No equivalent API. You can detect if screen recording is active using CGWindowListCopyWindowInfo and checking for screen-recording-capable processes, but you cannot prevent it. Your best option: periodic screenshot hash comparison (if the candidate's screenshot output looks like it's being recorded, the content will appear in mirrored form).

Linux: Wayland compositors (Sway, GNOME Wayland) have per-app capture permissions, X11 does not — anything can capture anything. Treat Linux as minimum security tier.

Clipboard Security Implementation

clipboard monitoring strategy (JavaScript in WebView) 
// Strategy: don't block paste — DETECT and RECORD it
// Blocking paste creates a terrible UX and is easily bypassed (right-click menu)

document.addEventListener('paste', (e) => {
  const content = e.clipboardData.getData('text/plain');
  const hash = sha256(content);
  const charCount = content.length;
  
  // Heuristics for suspicious paste
  const isSuspicious = (
    charCount > 50 &&                     // Not just pasting a variable name
    looksLikeCode(content) &&            // Contains code-like patterns
    !isFromOurPlatform(hash)              // Not a paste of our own question text
  );
  
  emitEvent({
    type: 'CLIPBOARD_PASTE',
    severity: isSuspicious ? 'high' : 'low',
    metadata: {
      contentHash: hash,
      charCount,
      targetField: getActiveFieldId(),
      isSuspicious,
    }
  });
  
  // Do NOT preventDefault() — that creates UX problems
  // Flagging is sufficient; human review will assess context
});

D

Tech Stack — Justified

Frontend — Exam UI

React + Vite + Monaco Editor

react · monaco-editor · react-query

Monaco is VSCode's editor — used by HackerRank, Codeforces, nearly everyone. It provides language servers, syntax highlighting for 50+ languages, and excellent keyboard handling out of the box. The alternative (CodeMirror 6) is lighter but less feature-complete for pro-level code editing. React Query handles exam state synchronization with smart cache invalidation.

Frontend — Admin Dashboard

Next.js (App Router) + Tailwind + Radix UI

next.js · shadcn/ui · tanstack-table

Next.js for SSR on the dashboard (data-heavy tables, review UIs). Radix UI primitives give accessibility for free — important for a B2B product. TanStack Table for the violation grid: virtualized rows handle 10k+ event logs without jank. Don't build your own table.

Backend — API Layer

Go (Fiber/Gin) + gRPC for internal

go · fiber · grpc · protobuf

Go for the main API layer: excellent concurrency primitives, low memory footprint at scale, fast compile times. At 10k concurrent WebSocket connections, Go's goroutine model handles this trivially; Node.js event loop becomes a bottleneck. Internal service calls use gRPC for type safety and performance. Python only for the ML proctoring pipeline where library support matters more than throughput.

Code Execution

Firecracker MicroVMs

firecracker · containerd · judge0-compatible API

Firecracker is what AWS Lambda runs on. MicroVMs boot in ~125ms, provide true kernel isolation (not just container namespaces), and support memory/CPU limits natively. gVisor is an alternative (more compatible, less isolation). Never run untrusted code in plain Docker — a container breakout is game over. Judge0 is open-source and battle-tested; use its API contract, implement your own execution backend.

Real-Time

uWebSockets.js + Redis Pub/Sub

uws · ioredis · kafka

uWebSockets.js is 10–20x faster than ws and handles 100k+ concurrent connections per server. Socket.io is friendly but carries overhead; drop it at scale and use raw WS with your own protocol. Redis Pub/Sub for fan-out within a datacenter. Kafka for durable event streaming — if your WebSocket server dies, Kafka retains events so the proctoring consumer doesn't miss signals.

Video Pipeline

mediasoup + FFmpeg + S3

mediasoup · sfuserver · ffmpeg · aws-s3

mediasoup is the best open-source SFU — used at scale, supports simulcast, is written in C++ with a Node.js control plane. For async proctoring, skip the SFU entirely: client sends HLS segments (6s chunks) directly to pre-signed S3 URLs. FFmpeg cluster for transcoding and stitching. Cloudflare R2 as an S3-compatible alternative (~50% cheaper egress).

Primary Database

PostgreSQL + TimescaleDB + Redis

postgres · timescaledb · ioredis

Postgres for everything transactional (users, exams, submissions, results). TimescaleDB extension for the event log — time-series queries (find all events between T1 and T2) are orders of magnitude faster with hypertables. Redis for session state, real-time integrity scores, distributed locks (exam start/end), and WebSocket room membership.

Native Client

Tauri (Rust) + TypeScript WebView

tauri · rust · @tauri-apps/api

Tauri uses the OS-native webview (WebView2 on Windows, WKWebView on macOS) rather than bundling Chromium. This means a 5MB binary instead of 150MB (Electron). Rust handles the native layer (process enum, clipboard hooks, multi-display detection). The webview runs your existing React exam UI unchanged. IPC bridge is typed via Tauri commands — clean, fast, secure.

Message Queue Strategy

Kafka for all anti-cheat events and video upload notifications. Topic-per-exam-session (or shard by candidateId). Retention: 7 days minimum (events needed for dispute resolution). Consumer groups: (1) real-time scoring consumer updates Redis integrity score in <100ms; (2) AI analysis consumer batch-processes events async; (3) storage consumer writes to TimescaleDB.

SQS/BullMQ for job queues: video stitching jobs, report generation, email notifications, AI inference batch jobs. Don't use Kafka for these — SQS FIFO or BullMQ (Redis-backed) is simpler and sufficient.

WebSocket Scaling — The Hard Problem

At 10k concurrent WebSocket connections, you cannot rely on sticky sessions and a single server. Use a shared state model: connection state lives in Redis, not in-process. When a WebSocket server scales down and a client reconnects to a different pod, the new pod fetches session state from Redis and resumes seamlessly.

Use Redis Pub/Sub with a consistent-hash ring for fan-out: each WebSocket server subscribes to its client's channels. When an admin sends a message to a candidate, it publishes to Redis; the candidate's connected pod receives and forwards. This scales to 50k+ connections across pods without a mesh.

Code Execution Scaling

The judge is your spikiest workload. At exam start, everyone submits simultaneously. Design for burst: pre-warm MicroVM pools 5 minutes before exam start (pull exam metadata, know how many candidates). Use a queue (BullMQ) in front of judges — submissions aren't dropped, they queue. Target P99 execution return in under 5 seconds including queue time. Each Firecracker VM uses ~25MB RAM; a c5.4xlarge with 32GB can run 1,000+ concurrent VMs after overhead.

Video Storage Cost Optimization

At 1 Mbps per candidate, 10,000 candidates for a 2-hour exam = 10,000 × 2hrs × 1Mbps = 9TB of raw footage per exam event. At S3 standard ($0.023/GB) that's $207 in storage. The bigger cost is ingress from clients (free on AWS but TURN server data transfer isn't) and CPU for any transcoding. Strategies:

  • Use 720p instead of 1080p — 95% of proctoring value is in facial recognition, not reading text.
  • Encode on the client (WebM/VP8 at 400kbps) rather than sending raw — reduces server-side transcoding.
  • Store to S3 Intelligent-Tiering — recordings older than 30 days move to Glacier automatically.
  • Only store video segments around flagged events at full quality; store other segments at lower quality (3fps instead of 30fps).

Load Balancing Architecture

Two-tier: (1) Cloudflare / AWS Global Accelerator for global anycast routing, DDoS protection, and TLS termination. (2) Internal application LB (ALB) with path-based routing: /ws/* → WebSocket pods, /api/* → API pods, /judge/* → Judge service. Separate health check endpoints per service class. WebSocket connections require sticky sessions on upgrade path only — after upgrade, the connection is sticky to the pod it landed on.

VM Detection

VM fingerprinting heuristics (Rust) 
fn is_likely_vm() -> (bool, Vec<String>) {
    let mut signals: Vec<String> = Vec::new();
    
    // 1. CPUID hypervisor bit (bit 31 of ECX in leaf 1)
    if cpuid_hypervisor_present() { signals.push("cpuid_hv_bit".into()); }
    
    // 2. Known VM vendor strings from CPUID leaf 0x40000000
    let vendors = ["KVMKVMKVM", "VMwareVMware", "VBoxVBoxVBox", 
                   "Microsoft Hv", "XenVMMXenVMM"];
    if let Some(v) = get_hypervisor_vendor() {
        if vendors.iter().any(|&s| v.contains(s)) { 
            signals.push(format!("hv_vendor:{}", v)); 
        }
    }
    
    // 3. SMBIOS/DMI check (on Windows via WMI, macOS via IOKit)
    if let Some(m) = get_system_manufacturer() {
        let vm_mfrs = ["innotek", "vmware", "parallels", "qemu"];
        if vm_mfrs.iter().any(|&s| m.to_lowercase().contains(s)) {
            signals.push(format!("smbios_mfr:{}", m));
        }
    }
    
    // 4. RDTSC timing anomaly (VM exits create measurable jitter)
    let jitter = measure_rdtsc_jitter(1000);
    if jitter > 500 { signals.push(format!("rdtsc_jitter:{}", jitter)); }
    
    (!signals.is_empty(), signals)
}
// Note: nested VMs and hardened VMs (Parallels with "hide VM") can pass these checks.
// Use as a signal, not a gate. Flag for human review, don't auto-disqualify.

AI-Assisted Cheating Detection

This is an async ML pipeline, not a real-time gate. Three models run in sequence after exam completion:

  1. Face detection + similarity: MediaPipe Face Detection across video frames. Compare to enrollment photo. Alert if: face disappears for >30s, face similarity drops (different person), multiple faces visible simultaneously.
  2. Object detection in webcam feed: YOLO-based detection of phones, books, secondary monitors. Books near keyboard during a coding test = suspicious. Flag, don't block.
  3. Code originality analysis: Semantic similarity between submitted code and known online solutions (GitHub, LeetCode). Embed both using a code-specific model (CodeBERT); cosine similarity > 0.92 → flag. Also check for solution structure: solving a "hard" problem in 90 seconds with perfect code is itself a signal.
False positive budget: If your AI flags 5% of candidates as cheating, and 90% of those are false positives, you have a major business problem. Tune for precision (few false positives) not recall (catch all cheaters). A missed cheater is bad; a wrongly disqualified genuine candidate destroys trust and opens legal liability.

Total per 10k-candidate exam event ~$1,900–$2,400
Key insight: At 10k candidates, your cost is roughly $0.20–$0.24 per candidate per 2-hour exam. The biggest cost drivers in order are: (1) Video streaming/TURN — 40%, (2) Compute for judge VMs — 35%, (3) AI inference — 15%, (4) Storage + CDN — 10%. If you want to cut costs: reduce webcam resolution, increase keyframe intervals on screen recording, use spot instances for judge VMs.

Biggest Cost Driver: Video at Scale

100k concurrent users at 1Mbps = 100Gbps ingress. AWS charges nothing for ingress but TURN relay, transcoding, and storage are expensive. At 100k candidates for a 2hr exam you generate ~50TB of recordings. S3 Intelligent-Tiering: ~$1,150 just for storage. Transcode at even 720p: $0.015 per minute on AWS MediaConvert = $0.015 × 120min × 100k = $180,000 just for transcoding. This is why you encode on the client and do minimal server-side processing. Target: zero server-side transcoding at ingestion time.

Key Challenges & Pitfalls

🍎

macOS Entitlement + Notarization Hell

Apple's notarization process takes 24–72 hours and can fail for opaque reasons. The hardened runtime blocks several APIs you'll want (JIT, unsigned dylib injection, task_for_pid). You need a paid Apple Developer account ($99/yr), a code signing certificate, and must submit every build for notarization. Accessibility + Screen Recording permissions require user action in System Preferences — you cannot automate this. Budget 2–4 engineering weeks just for macOS compliance, plus ongoing work every time you update entitlements.

⚠️

False Positive Rate Is Your Product's Reputation

If your AI says someone cheated and they didn't — you've potentially ended their career opportunity and exposed your customer (the employer) to discrimination claims. Every automated flag must have a human review step before it becomes an "accusation." Build your review queue before you build your ML model. Tune for >95% precision on "definite cheat" classifications. Keep a separate "suspicious" bucket that doesn't get communicated to employers unless they specifically request it.

🔗

WebSocket Connection Reliability at Scale

A 2-hour exam with 10k candidates means 10k WebSocket connections that must survive NAT timeouts, mobile network switches, hotel wifi hiccups, and server deployments. Implement heartbeat pings every 25 seconds. Buffer events locally on the client with a sequence number. On reconnect, replay missed events from the buffer. The server must handle reconnect as idempotent — re-delivering already-received events (identified by eventId) must not double-count. This is harder than it sounds and is where most real-time systems break.

🛡️

The UX vs Security Tension Is Constant

Every security measure you add degrades UX. Requiring a native app install will cause ~15–30% of candidates to drop off before starting. Blocking clipboard will make candidates who copy-paste their own notes furious. Restricting secondary monitors will affect candidates with accessibility needs (vision impairments who use screen magnification on a second display). You need configurable security levels (high-stakes vs screening) and a clear appeals process. Design for the honest majority, not just the cheating minority.

⚡

Code Judge Tail Latency

P99 execution latency matters more than average. A candidate who submits and waits 30 seconds for a result while their timer runs gets a terrible experience. Firecracker VMs have ~125ms boot time but cold-start includes filesystem setup, language runtime init, and your test harness. For Python, this can reach 800ms–2s cold. Pre-warm VMs by keeping a hot pool of initialized, snapshotted VMs per language. Load the snapshot instead of booting from scratch — this gets cold-start to <100ms. Implement a 5-second timeout on the judge client side; show a "running" state and poll rather than holding the WebSocket open.

🎥

Video Storage at Scale Is a Budget Trap

S3 storage is cheap per GB but the egress cost for reviewers streaming recordings adds up. An admin reviewing a 2hr recording downloads 500MB–1GB of video. At 1000 review sessions/month at $0.09/GB egress = ~$90–$180/mo just in egress for review. Use CloudFront signed URLs for video delivery — CloudFront egress is cheaper than S3 direct egress and caches repeated views. Also: implement video clipping so reviewers only download the 5-minute segments around flagged events, not the full recording.

⚖️

Legal & Compliance in Multiple Jurisdictions

Recording webcam video of candidates triggers GDPR (EU), CCPA (California), BIPA (Illinois biometric privacy), and various other regulations. You need explicit informed consent before starting any recording. You must disclose retention periods (30/60/90 days is common). GDPR requires data deletion upon request and the ability to export data. Illinois BIPA requires written release for biometric identifiers — facial recognition falls under this in Illinois. Hire a privacy attorney before entering enterprise contracts. SOC 2 Type II certification is required by most enterprise customers — start the audit process in Phase 3.

🤖

AI-Assisted Cheating Is Genuinely Hard to Detect

A candidate using ChatGPT on a phone camera pointed at their screen, wearing an earpiece, and typing the solution themselves will pass most proctoring systems. This is the industry's open problem. Behavioral signals help: abnormal speed (solving hard problems in under 60 seconds), unusual typing patterns (long pauses followed by bursts), off-screen gaze. But these are probabilistic. Your best defense here is assessment design: use problems that are hard to Google (novel, company-specific, contextual), time-box tightly, use follow-up technical interviews. Proctoring deters casual cheating; it doesn't stop sophisticated attacks.

Summary: The Five Real Engineering Bets

  1. Client security depth vs. distribution friction tradeoff — native app gives more hooks but will cost you 20% of candidates. Start web-based, gate native to high-stakes tier.
  2. Reliable event delivery is your core infrastructure challenge — lose an anti-cheat event and your integrity reports are wrong. Build the event pipeline correctly before the ML pipeline.
  3. Video is your largest cost and the hardest to optimize — make client-side encoding a first-class concern from day one.
  4. False positive management is a product problem, not a tuning problem — design human review workflows before shipping AI-driven flags.
  5. macOS will take 2x as long as you think — plan for it explicitly. Don't treat it as a port of Windows; it's a different security model entirely.
